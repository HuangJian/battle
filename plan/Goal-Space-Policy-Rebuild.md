## 0. 读我

### 0.1 一句话背景

Intent NN（M8，it38）在 hard 上 **75.0%**，God-AI 当前基线 **75.86%**（§1）。未能超越的根因不是训练，
是**决策权分配**：执行器把 NN 的输出当成 God-AI 候选链的**剪枝掩码**，导致
**NN 可达行为集 ⊆ God-AI 可达行为集**（§2-R1）。本方案把动作空间从「选哪个意图」换成
「**站哪个格子**」，并把 NN 输出从**掩码**改为**参数**。

### 0.3.1 ⚠️ canary 的统计功效（评审 D7：350 局检测不出 2pp）

**问题**：canary 门②原写"**60-seed 净收益过线**"= 350 局（SE **2.3pp**）。
按配对差 2σ 计，350 局只能检测出 **≈4.5pp** 量级的差异 ——
而手册论证的目标收益是 **T9 ≥2pp**。
⇒ **真收益 2pp 时 canary 大概率判"没过线"（type-II 漏报），本可成功的路线被误杀。**

**定案 —— canary 门降格为方向性**：

| 阶段 | 局数 | SE | 门 |
|---|---|---|---|
| **T5 / T9a（canary）** | 350 | 2.3pp | ① 反事实给得出梯度 ② **配对差方向为正**（**不要求显著**） |
| **T9（主门）** | 2100 | 0.93pp | 配对差 ≥2pp **且 CI 下界 > 0**（这才是为 ±2pp 设计的） |

**明示 type-II 风险**：T9a 若"方向为正但不显著" ⇒ **不判死**，
T9 可选 **700 局小规模先验**复核（SE 1.9pp）再决定停或继续。

## 6. 目标契约

### 6.1 接口（`src/nn/goal-contract.ts`，新建）

> ⚠️ **本节经评审 A2 修订**：删两个僵尸字段、`premise` 语义重新分层。

```ts
export interface GoalContract {
  cell: { row: number; col: number }      // 去哪（过可达性掩码 + §9.4.0 的 25×25 合法顶点）
  premise: Premise                         // 为什么去（**通用环境谓词**，非目标格专属）
  T: number                                // 最长承诺 tick
  travelEst: number                        // 预计到达 tick
  bornTick: number
}

export interface Premise {
  /** E1 用：通用动态谓词，对所有合约统一适用，每 tick 可求值；任一为假 ⇒ E1 */
  predicates: Array<(w: World, c: GoalContract) => boolean>
  /** 归因用（**不参与 E1 判定**）：静态/准静态地图条件的可读标签 */
  label: string
}
```

**已删除的两个僵尸字段**（`targetCell` / `K`）：target 头与 K 头已在 §8.3.0b 被砍，
但接口没同步 ⇒ 实现者在 T8/T8.5 会无所适从。"打谁"归 L3（`fire_head`，§10.3.2）。

#### 6.1.1 ⚠️ premise 的语义断层：热图不产出"理由"（评审 A2）

**断层**：网络输出是**纯空间热图**，`selectGoal` 返回一个 `cellIndex`。
⇒ **`GoalExecutor` 根本不知道网络"因为什么"选了那一格**，`premise` 从哪来没人说清。
若留空或恒 `true` ⇒ **E1 永远不触发，退化为死代码**。

**⚠️ 明确否决的解法**：通过格子坐标"反推意图"（如"在基地附近 ⇒ 是防守"）
= 重新引入一套启发式意图分类层 —— **正是本方案要摆脱的东西**（R4/§5）。

**定案 —— premise 分两层，只有第一层参与 E1**：

| 层 | 内容 | 求值时机 | 参与 E1? |
|---|---|---|---|
| **① 通用动态谓词** | 对所有合约**统一适用**的环境有效性条件，与"选了哪一格"无关：<br>· 基地未被摧毁<br>· 玩家未处于不可控状态（冰冻/失控）<br>· 关卡仍在进行 | 每 tick | ✅ **是** |
| **② 归因标签**（`label`） | 静态/准静态的**地图与局势条件**，供仪表与失效归因：<br>· `detectCentralBreachRisk(world)`（§16.1 原型一）<br>· 砖密度档位（原型二） | 选定时一次 | ❌ 否 |

**为什么这么分**：§16.1 原本让 `premise = detectCentralBreachRisk(world)` 充当 E1 判据，
但该函数**随地图静态成立** ⇒ 一局之内不会翻转 ⇒ **作为 E1 判据是死代码**。
它真正的价值是**归因**（"这一局玩家为什么一直守中路"），所以移到 `label`。
**E1 的活由通用动态谓词承担** —— 它们与具体目标无关，天然可每 tick 求值。

⇒ `premise.predicates` 的候选集在 **T8-minimal** 定稿（复用 §6.5 已有的纯函数）；
`label` 的取值集合随 §16 的两个原型扩充。

**可满足性校验（选定时执行）**：**只拒绝不可达**（`travelEst = ∞ ⇒ 拒绝重选`）；
`T` 的唯一职责是**重评估节奏**（§6.2 E4 / §6.3 慢心跳），**不是移动半径上限**。

> ⚠️ **本节于 2026-08-29 修订（T9a 归因，commit `b84c012`）**：旧版写
> "`travelEst ≤ T` 否则直接拒绝重选"，与 §6.2 的 `T = 承诺期/心跳` 语义**内在矛盾** ——
> `T=240` 只够走 ~10 格（23 tick/格），坦克到达首个目标后**任何更远的目标被永久拒绝**，
> 而 E4 是"延期"不是"放弃" ⇒ 契约被永久续约 ⇒ **坦克冻结在原地**（实测 989 tick 走 5 格，
> T9a 门② −78.8pp 的直接成因之一）。地图级 `travelEst` 典型 300–500 tick，
> 与承诺期不在一个量纲。**教训：承诺期（何时重想）与可达半径（能去哪）是两个自由度，
> 不得由同一个 T 承担。**

### 6.2 失效条款（触发**重新评估**，非立即放弃）

| # | 条款 | 判据 | 是否过网判定 |
|---|---|---|---|
| E1 | 前提不成立 | `premise.predicates` 任一为假 | **否**（纯谓词） |
| E2 | 出现明显更优机会 | `V(new) − V(cur) > δ` | 是 |
| E3 | **静态地形**不可达 | `reach-mask` 该格 `≡ −Infinity` | **否** |
| E4 | 超出承诺期 | `tick − bornTick > T` | 是（慢心跳） |
| E5 | 安全位移超限 | 累计被 dodge 位移 > N tick | **否** |

**定序固定**：`E3 > E1 > E5 > E4 > E2`（先判可行性 → 前提 → 最后才比价值）。

### 6.3 触发：事件驱动 + 慢心跳

- E1/E3/E5 **纯谓词**，不过网 ⇒ 可每 tick 求值
- 需过网的（E2/E4）与 **慢心跳 150–300 tick** 才触发前向
- ⇒ 网络前向从"每 30 tick 一次"降为**按需**，直接缓解 **110–170 ms/次**的推理预算
  （⚠️ 此处原引用 41 ms，是 §16.1 已作废的旧值；评审 d2 指出，已更正）

**与 §25 risk-gated 负结果（−4.3pp）的关系**：risk-gated 让**重选**更频繁 ⇒ 抖动。
本设计把**评估**与**切换**解耦：评估可频繁，切换必须过 δ 门。

### 6.4 迟滞 δ

作用在**价值差**上（原 `SWITCH_MARGIN=0.15` 作用在意图 logit 差上，层次错了）。
**δ 从数据标定**：对每次 E2 放弃做反事实重放比"放弃 vs 坚持"，取最优分位。
不对称：紧急度上升 ⇒ δ 降低；平稳 ⇒ δ 升高。

#### 6.5.2 ⚠️ δ 与 ε 的措辞（评审 d6：量纲不同，"同源"易被实现成"同值"）

- **δ** 作用在 **value 差**（网络输出，量纲随训练漂移）
- **ε** 作用在 **窗口分数差**（§11.3 手工打分，量纲固定）

⇒ 措辞改为「**共用数据管线、分别标定**」：

### 6.6 ⚠️ E3 必须只认静态地形，不得被动态单位触发（评审 A4）

**风险**：旧版 E3 判据写作"目标不可达/**被占**"——"被占"这个词有歧义，
实现者很可能写成"目标格上有敌坦 ⇒ E3 触发"。那会造成灾难性抖动：

- 4 辆敌坦持续巡逻，狭窄通道里**每 5–20 tick** 就会有敌坦临时压在玩家路线或目标格上
- 一旦触发 E3 ⇒ 契约立即失效 ⇒ 重跑网络重选
- ⇒ **150–240 tick 的承诺期在遭遇战中坍缩成 5–10 tick 的高频重选**，
  正是 §6.3 想避免的抖动（也是 §25 risk-gated −4.3pp 的成因）

**代码核对**：`pathfind.ts:49-55` 的 `blockedCell` 是**可选参数**（`blockedCell?: Cell | null`），
默认**不带** ⇒ 默认 `findPath` **只看地形，不把敌坦当障碍**。
但若 `GoalExecutor` 传入 `blockedCell`（或实现者自行加占用检查），E3 就会开始误报。

**定案**：

| 项 | 定案 |
|---|---|
| **E3 判据** | 严格限定为 **`reach-mask` 该格 ≡ −Infinity**（静态地形不可达：<br>钢墙完全隔绝 / 自身被围 / **第 25 行列的 51 个越界顶点**（§9.4.0）） |
| **动态敌坦占位** | **不触发 E3**。交给 **L0（dodge）** 与 **L2（`Navigator` 局部等待/微绕行）** |
| **禁止** | 不得把"目标格当前被坦克占据"写进 E3 |
| **验收（T8-minimal 回归测试）** | 构造"路线中/目标格上出现移动敌坦"的场景，<br>断言**契约不被撤销**、目标格不变、`pathfind` 走局部绕行 |

> 附带好处：E3 只认静态地形 ⇒ "可达性"是一个**准静态属性**（只在砖墙被摧毁时变化）
> ⇒ `reach-mask` 可缓存，只在地形变更 tick 重算 —— 这进一步压低 T3 的运行开销。

### 6.7 ⚠️ 契约分两期（评审 G4：E2/δ 存在循环依赖）

**问题**：T8 排在 T9a 之前，但
- **E2**（`V(new) − V(cur) > δ`）需要 value 头 —— 而 value 头是 **PPO 产物**
  （`intent_net.py:44` 确认 `value_head` 挂在 `with_value=True` 的 RL 变体上），
  T8/T9a 处于 BC/小 PPO 阶段，**value 估计尚不可信**；
- **δ 标定**（§6.4）要求"对每次 E2 放弃做反事实重放"——这是又一条**没有任务卡的数据管线**。

⇒ 旧版让契约机制**先于证据**，循环依赖。

**定案 —— 契约两期化**：

| 期 | 条款 | 说明 |
|---|---|---|
| **T8-minimal（canary 期，~1d）** | **E1 / E3 / E5 + 固定 T（心跳）** | 全部**纯谓词**，无需网络、无需 value。
E2 **关闭**（或用"上一窗口分数差"作免网代理） |
| **T8-full（T9 通过后）** | 启用 **E2 + δ 标定** | 此时 value 头已由 PPO 训出；
δ/ε 标定管线与 T9 全量训练**合并排期** |

**好处**：
1. 消除"value 头不存在"的循环依赖
2. T8 从 2d 降到 **~1d**
3. **§15-R8「契约长成缝合怪」的最好防御就是初版契约越小越好** ——
   先用 3 条纯谓词跑通 T9a，再决定是否值得加 E2

### 6.8 ⚠️ E2 的 V 语义（评审 D3：单标量 value 头回答不了"哪个目标更好"）

**问题**：§6.2 写 `V(new) − V(cur) > δ`，但 §8.3 只有一个 `hiddenInject(137) → 1`
的**标量** value 头（且核对 `infer.ts:299-300` 确为 `Float32Array | null`：
"**BC/intent checkpoints without a value head leave this null and valueOut reads 0**"）。
**单标量 V(s) 无法比较"目标 A vs 目标 B"** —— 实现者面对这个空洞只会瞎猜。

**定案 —— E2 = 状态价值跳变触发重评估（不比较目标）**：

```
E2 触发条件：  V(s′) − V(s) > δ
E2 触发动作：  重跑 selectGoal（§9.4.1 热图 argmax 重新选格）
```

理由：**热图本身就是逐格的"目标价值面"**，重选天然完成了目标比较 ——
不需要 goal-conditioned `V(s, goal)`（那是新网络头，§8.3 没有，也不该混进 T8-full）。

δ 标定口径随之变为「**价值跳变分位**」（而非"目标价值差分位"）。
若将来真需要 goal-conditioned value ⇒ **单独开卡**，不进 T8-full。

## 7. 分层规格

```
L0 安全层   dodge —— 硬约束，不可被策略否决；只能"位移"目标不能"取消"目标
L1 目标层   NN：goal 热图 + engage + value（**只此三个头**，§8.3.0）
L2 路径层   pathfind 到 cell；代价权重参数化（§9.2）
L3 开火层   K 驱动的射击决策（§10）
```

**仲裁纪律**：L0/L3 之间是**硬约束 + 单一裁决者**，**禁止优先级级联**（否则重长缝合怪）。

### 8.1.1 ⚠️ inject 9 维的 goal-space 语义（评审 P5：旧版未定义）

现 inject 是**意图专用**的（`intent-executor.ts:203-205`）：

| 维 | 语义 | 范围 | 用途 |
|---|---|---|---|
| 0 | `prevGoalRow / 26` | [0,1] | 上一目标位置（时序连贯性） |

  保留维恒 0 属死参数，代价可忽略（4×137 = 548 个权重）。
  改成 129/131 也能跑，但会牵动 golden 文件与所有形状断言 ⇒ **不值得**。
- **🚨 duration 分布漂移是 OOD 风险，不只是"次生问题"（评审 a1 升级）**：

  | 阶段 | 决策周期 | `duration` 取值 | 归一化后（维 2） |

  **进入未训练过的激活区（OOD）**，输出不可信。

  1. **标注语料必须按比例混入长承诺样本** —— T6 产出的语料里，

  3. **T9a 附加检查⑤**：画出 duration 维的取值分布直方图，
     断言 BC 语料与部署采样**区间重叠度 > 50%**

#### 8.3.1 ⚠️ 必须有"不交战"表示（评审 F10 + P3 改写）

被删的 `enemy_head` 有 **none 槽**（index 0），而二元决策若只留 `fire_head`，
**每个窗口都会产出一个"打"的倾向**，场上没有值得打的敌人时无法表达"不打"。
旧版指望 L3/K 去否决 —— 但**标签层面没有"无目标"的定义**，BC/PPO 无法学。

**定案**：独立二元头 `engage`（`hiddenInject(137) → 2`），语义为
**"本窗口要不要主动交战"**（而非"打谁" —— 打谁归 L3 的 `fire_head`）：

| `engage` | L3 行为 |
|---|---|
| **0** | **不主动交战**：只在顺路（正前方）且满足 K 门控时开火 |
| **1** | **主动交战**：允许为交战转向（付 §11 的偏离成本），选敌由 `fire_head` 定 |

- 理由：把"有没有目标"压进热图的峰值置信度是脆弱的（峰值高低与"是否有敌"不是同一件事）
- **P3 改写说明**：target 头已砍（§8.3.0b），`engage` 从"target 的开关"改为
  **直接门控 L3 的交战意愿**。语义更窄、标签不变（§8.3.2）、消费方更明确。

⇒ 这是 T7 的**硬规格**，不定不能开工。

#### 8.3.2 ⚠️ engage 标签的判定准则（评审 G5：旧版"值得"是循环定义）

旧版写"该窗口**有无值得**指定目标"——"值得"若由"网络将来该学会的判断"定义，就是循环。

**定案（一行定义，绑到 §11.3 的窗口分数，不再循环）**：

```
engage = 1   ⟺   max_{c ∈ 候选集} score(c)  −  score(当前格)  >  ε
```

- `score` = §11.3 的窗口级打分（**已有、可计算、不依赖网络**）
- `当前格` 必在候选集内（§11.2 已含），作为"什么都不做"的基线
- **ε 初值**：取 0（任何正增益都算值得），扫 {0, 0.5×σ, 1×σ}，σ = 窗口分数的滚动标准差
- **ε 与 δ 同源标定**（§6.4 的迟滞阈值）——两者都是"差多少才算数"的阈值，
  标定管线共用，见 G4 的处置

**负例**：语料中 `engage=0` 的样本必须显式保留（正是那些"留在原地更好"的窗口），
否则网络学不会拒绝。⇒ 写入 **T6.1(c)**。

### 8.4 为什么不用 52 路行列分解

`p(r,c)=p(r)·p(c)` 是乘积分布：两个真实模式 `(r1,c1)/(r2,c2)`、边际各 0.5 ⇒
四组合各 0.25 ⇒ **50% 概率质量落在幻影格**。参数对比：

| 方案 | 参数 |
|---|---|
| 676 路全连接 | 92,612 |
| 52 路行列分解 | 7,124（**且有表达损失**） |
| 173 路 coarse-to-fine | ≈23,800（链式法则，零损失） |
| **1×1 卷积热图** | **65** |

**算力账**：输出层只占推理 **0.25%** ⇒ "减运算量"动机不成立。

`computeThreatCostsImpl` 已于 M0.5 退役、当前无人填充 ⇒ **零新增结构即可注入威胁容忍**。

### 9.4 可达性掩码（分层）

| 层 | 含义 | 掩码值 |
|---|---|---|
| blocked（钢 / 基地 / 水无船 / 界外） | **绝对不可达** | `−∞`（硬遮） |
| walk-reachable | 纯行走可达 | `0` |
| **carve-reachable** | 需凿 k 块砖，代价 ≈ 8×k tick | `−λ·k`（**带代价，不硬遮**） |

掩码**不能只做 0/1，要带代价**，否则网络选不到"凿开就到"的格子（§16.2）。

#### 9.4.0 🚨 26×26 网格里只有 25×25 个合法坦克顶点（评审 A3，已实测核对）

**核对 `src/utils/grid-search.ts:53`**：

```ts
// A 2×2 tank needs cols [col, col+1] and rows [row, row+1] inside the grid.
if (col < 0 || col + 1 >= GRID || row < 0 || row + 1 >= GRID) return false
```

`GRID = 26`（`constants.ts:17`），`TANK = CELL*2 = 32`（`:23`）占据 2×2 格
⇒ **坦克左上角顶点 `(row, col)` 的合法范围是 `[0,24] × [0,24]` = 625 个**，不是 676。

```
第 25 行（26 格）∪ 第 25 列（26 格）− 重复计数的 (25,25)
  = 26 + 26 − 1 = 51 格（占 676 的 7.5%）   ← 物理上永远不可作为坦克顶点
```

**硬要求**：

| 位置 | 要求 |
|---|---|
| **T3 `reach-mask.ts`** | `∀ r === 25 ∨ c === 25 ⇒ mask[r*26 + c] ≡ −Infinity`（**51 格永久硬遮**） |
| **T9a.1b 粗网格** | 26×26 切成 13×13 个 2×2 块，**`Block(12,12)` 含 `(24,24)(24,25)(25,24)(25,25)`，<br>其中只有 `(24,24)` 合法** ⇒ 块内 argmax **必须先过滤越界格**，否则选出 `(25,25)` 会越界 |
| **T6 候选生成器** | 候选格不得落在第 25 行/列（否则标签指向不可达格） |

**验收（两处单测）**：
1. `reach-mask.test.ts`：断言 `mask[25*26 + c]` 与 `mask[r*26 + 25]` 全为 `−Infinity`（51 项）
2. `coarse-block.test.ts`：`Block(12,12)` 内有效候选**仅且仅有 `(24,24)`**

> **为什么这条之前没人发现**：obs 编码与网络输出都是 26×26（对齐 `tileMap.grid`），
> 但**动作空间是"坦克顶点"而非"地形格"**，两者维度巧合相同、语义不同。
> 这个不等价性在 intent 时代不存在（意图不是格子），是 goal-space 引入的新陷阱。

#### 9.4.1 ⚠️ 推理时的选格算法（评审 F9：旧版完全没定义）

**定案（推荐"推理前强制 mask"）**：

```ts
// 训练与推理使用同一函数，保证 train/infer 一致
function selectGoal(heat: Float32Array /* 676 */, mask: Float32Array /* 676 */): number {
  let best = -1, bestV = -Infinity
  for (let i = 0; i < 676; i++) {
    if (mask[i] === -Infinity) continue        // 绝对不可达：硬遮
    const v = heat[i] + mask[i]                // carve-reachable: 代价扣分，不遮死
    if (v > bestV) { bestV = v; best = i }
  }
  return best
}
```

关键决策（**必须二选一，不能骑墙**）：

| 方案 | 训练标签 | 优劣 |
|---|---|---|
| **✅ 推理前强制 mask（采用）** | 标签只落在**可达格** | 网络**不必学可达性**，样本效率更高；
训练/推理一致；最安全 |
| 让网络自学可达性 | 标签须含不可达格的**负例** | 训练更贵、更慢，且出错即卡死 |

**有序回退**（`best === -1` 时，理论不该发生，但必须定义）：
`原地停射` → `当前格邻域最近可达格` → `God-AI 兜底`（§9.2.1 旁路）

#### 9.4.2 λ 量纲与平局（评审 G9）

| 项 | 定案 |
|---|---|
| **λ 初值** | **0.5**（每需凿 1 块砖，扣 0.5 热图 logit）。热图 logit 经 softmax 前量纲未定，
λ 需与热图同标 —— **先定 0.5，由 T9a 结果校准** |
| **λ 标定** | 若 T9a 显示"该走凿砖近路却不走" ⇒ λ 偏大，下调；
若"乱凿墙" ⇒ λ 偏小，上调。扫 {0.25, 0.5, 1.0} |
| **平局** | `>` 严格大于 ⇒ 平局时取**索引最小格**（行主序）。**恰好确定**，
但 T8 单测必须显式断言："相同 `heat+mask` ⇒ 固定选格"，防止将来改成 `>=` 或换遍历序时静默漂移 |

**训练侧要求**：反事实候选生成器（§11.2）产出的候选**必须先过 `selectGoal` 的可达性
过滤**，否则会产出永远到不了的标签。

#### 9.4.3 ⚠️ λ 的 train/infer 结构不一致（评审 P4，已核对并加一条未识别的坑）

**不一致（评审指出，属实）**：

| 侧 | 式子 | carve 格的处理 |
|---|---|---|
| **推理** §9.4.1 | `selectGoal = argmax(heat + mask)`，`mask = −λ·k` | **扣掉** λ·k |
| **训练** §11.5 | `p_i ∝ exp(s_i / τ)`，只用窗口分数 `s_i` | **不扣** |

⇒ 网络被训成"对值得去的 carve 格输出高 logit"，推理却要减 λ·k
⇒ **carve 近路在推理被系统性低估**，而"清墙开路"正是 §16.2 原型二的解法。

**定案：(a) 训练侧同构扣减，但 λ 必须是训练时旋钮**

```python
# shard 存原始 (s_i, k_i)，λ 在构造 loss 时才介入
p_i ∝ exp((s_i − λ·k_i) / τ)      # i ∈ 候选集
```

| 要求 | 说明 |
|---|---|
| **shard 必须存 `k_i`** | 每候选格的需凿砖数。**否则 λ 一改就要重新标注**（§11.9：2100 局 40 min） |
| **λ 是训练超参，不是标注常量** | §9.4.2 要扫 {0.25, 0.5, 1.0} ⇐ 只有训练时可扫才成立 |
| **τ 与 λ 联合扫** | 两者都在 softmax 前，量纲耦合 |

**➕ 评审未识别的坑：双重计数**

若 §T6.1 的 rollout 用**开启 carve 的 pathfind** 驱动，则 `s_i` **已经内部包含了凿砖
的时间代价**（到得晚 ⇒ 窗口内收益少）。此时再减 λ·k 是**重复惩罚**。

| 标注期 carve 开关 | `s_i` 是否已含凿砖代价 | λ 的正确角色 |
|---|---|---|
| **OFF**（当前默认，§16.2） | 否 —— carve 格根本不可达，<br>**拿不到 `s_i`** | λ 是**唯一**的代价来源，取大值 |
| **ON**（T3 开门后） | **是** | λ 退化为**保守 tie-break 先验**，取小值 |

**⇒ 因此新增硬排序**：**T3（开 carvePath 门）必须先于 T6（标注）**。
否则 §9.4 那张"carve-reachable 带代价"的掩码**从来拿不到标签**，原型二的解法落空。
（与 §16.2 的结论一致，但那里只说"P3 必须过"，没把它钉成 T6 的前置。）

**λ 初值**：守 §9.4.2 的 0.5，`k_i` 已入库 ⇒ 训练时可直接扫，无需重标。
**验收**：T9a 检查"该走凿砖近路却不走"（§9.4.2 已有此检查项）。

### 10.3 延迟预算 K

- `K` = L1 标量输出（= 目标紧急度的倒数）

- 按方位默认：**正前方（在路径上）→ 开火**；**侧方 → 默认不开火，由 K 决定例外**；后方 → 不开火
- 应学出的例外：冰冻生效（**必须门控**，`Intent-Policy-NN-Plan.md` §12.2 缺陷① 就是冰冻期目标摇摆）·
  1★/2★ · 目标紧急度 · 威胁预测

#### 10.3.1 ⚠️ "预测击杀延迟"的实现规格（评审 D4 补充：分量其实已存在）

评审说 `FireControl.ts` 没有击杀延迟估算 —— **部分成立，但比估计的便宜**。
核对 `FireControl.ts:450-452 / 506-507`：**已有 lead-aim 拦截时序计算**

```
enemyTimeToCross  = perpDist    / enemySpeed
bulletTimeToReach = parallelDist / bulletSpeed
⇒ |enemyTimeToCross − bulletTimeToReach| ≤ tolerance 时开火
```

**`bulletTimeToReach` 正是击杀延迟的主分量**，可直接复用（不必新写启发式）。

**定案 —— 击杀延迟粗估公式**：

```
killLatency(e) ≈ turnTicks(curDir → aimDir)          // 0 若已对齐，否则 1 tick
               + ceil(distCells(player, e) × 6)      // 弹速 6 tick/格（§10.1）
               + alignTicks(e)                       // 若尚未共线，需走到共线的 tick（复用 pathfind）
```

- `turnTicks`、`distCells` 现成；`alignTicks` 复用 `findPath` 到共线格的代价
- **精度要求：粗估即可**（K 是预算上限，不是精确预测）⇒ 不做运动外推，按当前位置估
- 冰冻/静止目标 ⇒ `alignTicks` 项显著变小（自然鼓励冰冻期开火）

L3 的 K 叠加在它之上 |

### 11.5 ⚠️ 监督形式（评审 G3：旧版通篇没提"loss"，最大隐形返工源）

§11.1 产出的是"每 obs 一个正格"的**极稀疏**信号，而 §8.3 的输出是 26×26 热图。
**从标签到 loss 的映射没定义 ⇒ BC 无法开工。**

#### 11.5.1 定案：软目标 + 全 676 维稀疏 CE

```python
# 候选集 C（|C|=K≈12），每个候选带 (s_i, k_i)：
#   s_i = 窗口分数（§11.3）   k_i = 需凿砖数（0 = 纯行走可达）
# λ = carve 代价系数，τ = 温度 —— 两者都是**训练时超参**，不固化进 shard

p_i = exp((s_i − λ·k_i) / τ) / Σ_{j∈C} exp((s_j − λ·k_j) / τ)   if i ∈ C
p_i = 0                                                          otherwise

# loss：网络热图 logits z（676 维）对 p 做交叉熵
loss = CE(softmax(z), p)
```

| 决策 | 选择 | 理由 |
|---|---|---|
| **软目标 vs 0/1 硬标签** | **✅ 软目标** | argmax 把近似同分的候选压成 0/1，
**丢掉分数差携带的信息**；软目标天然利用它（评审佐证：§11.6 臂 B 的前提正是分数差有信息量） |
| **支持集：K 路 vs 676 路** | **✅ 676 路** | K 路 CE 会让**未评估格**的 logit 完全不受约束
⇒ 推理时可能意外胜出。676 路把非候选格压低，与 `argmax(z+mask)` 推理式一致 |
| **温度 τ** | 初值 **1.0**，扫 {0.5, 1.0, 2.0} | τ→0 退化成硬标签；τ→∞ 退化成均匀分布 |
| **λ·k 在训练侧扣除** | **✅ 见 §9.4.3** | 与推理 `argmax(z + mask)`、`mask=−λ·k` **同构**。
**shard 必须存 `k_i`** ⇒ λ 可扫而无需重标注 |

**已知假设（必须承认）**：676 路 CE 会把"从未被评估过的格子"也压低，
而它们未必真的差——只是没测。缓解靠候选生成器的覆盖度（§11.2 已含锚点/敌后/砖墙/原地/中点）
+ **§11.4 的候选截断规则** + **T6 输出的"候选集覆盖率"统计**。

**与推理的一致性**：`argmax` 对 softmax 单调不变 ⇒ 训练用 CE、推理用 `argmax(z+mask)` 是自洽的。

### 11.7 ⚠️ T 与 H 的约束关系（评审 D6：三者互不约束）

三处各自定义、互不约束：承诺期 **T**（T8"固定 T"，**未给值**）、

**定案 —— 约束 `T ≤ H`**：

| 项 | 定案 |
|---|---|
| **BC 阶段** | **硬约束 `T ≤ H`**。T8 验收须断言"T 与 §11.8 扫出的 H 满足 T ≤ H" |

| **T9 之后** | 由 **E4 放弃率**（T0 仪表）回调：放弃率过高 ⇒ T 偏长，下调 |
| **与 RL 视野** | `T ≤ H ≤ 210 tick`（RL 有效视野）是自然的中间关系；
若 H 扫出 480 > 210，说明标签视野超过 RL 信用分配能力 ⇒ 以 240 为上限 |

⇒ 这条把"T / H / RL 视野"三个独立旋钮合成**一条链**，避免标签与执行错位。

### 12.1 ⚠️ γ_step 不是常量 0.86（评审 k6）

§12/§12.2/附录 A 的 `γ_step = 0.86` 与"视野 ≈7 步"都是 **intent 步（dt=30）** 口径。
**goal 步的 dt = T**，而 T ≤ H ≤ 240（§11.7）⇒：

| 承诺步 dt | `γ_step = 0.995^dt` | 步域视野 `1/(1−γ_step)` | **tick 域视野 `dt/(1−γ_step)`** |
|---|---|---|---|
| 30（intent） | 0.860 | 7.1 步 | 214 tick |
| 120 | 0.549 | 2.2 步 | 267 tick |
| 240 | 0.301 | **1.4 步** | **343 tick** |

**关键**：步域视野掉到 1.4–2.2 步，**但 tick 域视野反而变长**（214 → 343 tick）。
⇒ **§13.2"RL 视野覆盖长时滞"的论证在 goal 步下更成立**，只是表述要改：
"视野 ≈N 步"失效，应写 **"视野 ≈ dt/(1−γ_step) tick"**。

**shaping 断言的泛化**（`compute_gae(dt=)` 已支持变步长，§13.1）：
步长可变时 telescoping 仍成立，只需把 `γ_step` 换成**逐步**的 `γ^{dt_k}`：

```
Σ_k γ^{t_k} · [ γ^{dt_k} · Φ_{k+1} − Φ_k ]  =  −Φ₀        （γ^{t_k}·γ^{dt_k} = γ^{t_{k+1}}）
```

⇒ **实现要求**：shaping 项改为 `γ^{dt_k} * Φ(窗末) − Φ(窗初)`，**不再用常量 γ_step**。
§12.2 的解析自检需按变步长改写（任取 dt 序列，断言上式成立）。

> **连带修正**：§11.9.1 的 **hb300 列与 §11.7 `T=H≤240` 矛盾** —— E4 在 T=240 触发，
> 心跳 300 永远不会发生。该列保留但标注"**仅作成本上界参考，非预期配置**"。

### 12.2 ⚠️ shaping 折扣必须与 γ_step 一致（评审 F3，已数学核对）

Potential-based shaping 定理要求 **塑形折扣 = 价值折扣**。本方案的折扣发生在
**意图步**（γ_step=0.86），因此：

| 写法 | 步级和 | 结论 |
|---|---|---|
| ❌ 步内 γ=1：`F = Φ(末) − Φ(初)` | `Σ_k γ^k[Φ_{k+1} − Φ_k]`<br>`= ((1−γ)/γ)·Σ_{k≥1} γ^k Φ_k − Φ₀` | **残留 (1−γ_step)=0.14 倍 Φ 的偏置** |
| ✅ 步级 γ_step：`F = γ_step·Φ(末) − Φ(初)` | `Σ_k γ^k[γ Φ_{k+1} − Φ_k] = −Φ₀` | **精确 telescoping** |

⇒ **实现要求**：窗口结算的 shaping 项改为 `γ_step * Φ(窗末) − Φ(窗初)`。
现 `intent-rl-reward.ts` 的 P1-8k3 断言（γ=1、闭合循环累积 ≈0）**需相应改写**——
它验证的是"步内 γ=1"，与新口径不一致。

**验收（挂 T0 或单测）**：
1. 解析自检：任取 Φ 序列，断言 `Σ γ^k[γΦ_{k+1} − Φ_k] === −Φ₀`（容差 1e-6）
2. 行为自检：闭合状态循环（绕一圈回初态）的累积 shaping ≈ 0（无 farming）

### 12.3 ⚠️ 奖励分量规格（评审 K4：旧版停在 G3 之前的水平）

**问题**：R6（七条根因之一）就是**奖励量纲错配**（`KILL=4.0` vs shaping 整局 ±1）。
但 §12 对新奖励只给了三个名词 + 一句"分量必须非饱和"——与 G3（通篇无 loss）同类，
只是位置从 BC 挪到了 RL。

三个具体缺陷：

| # | 缺陷 | 说明 |
|---|---|---|
| 1 | **"K 执行质量"是残留文本** | K 已被 P3 降为**规则参数**（§8.3.0b），不再是网络输出。<br>"K 执行质量"**既无可计算定义也无数据来源** |
| 2 | **三个分量无量级预算** | 相对量级完全没标定 —— 这正是 R6 的病史区，手册却连一张量级表都没有 |
| 3 | **"非饱和"无验收手段** | 没有卡负责检查各分量的数值分布与梯度贡献，<br>v7"分量存在但零梯度"复发**无人拦截** |

**定案 —— 三分量 + 量级预算 + 饱和检查**：

| 分量 | ① 定义式 | ② 量级预算（相对窗口分数量纲） | ③ 饱和检查 |
|---|---|---|---|
| **目标到达** | `+1` 若窗口末在目标格邻域（≤1 格），否则 `0` | 主项，**1.0** | 到达率须 ∈ (10%, 90%)；<br>否则目标格选得太难/太易 |

| **交战效率**（**替代"K 执行质量"**） | `命中数 / 开火数` 的窗口值 − 自伤否决触发率 | **0.3** | 命中比 ∈ (0,1) 且非常数；<br>自伤触发率须 >0（否则该分量恒为常数、零梯度） |

⇒ **删除"K 执行质量"**，理由记在 §8.3.0b（K 已是规则参数）。

**验收（挂 T0 仪表 + T9a）**：
1. **T0**：各分量滚动分位数（p10/p50/p90）进 `goal-telemetry`
2. **T9a**：各分量对 advantage 的贡献占比**非零**（全零 ⇒ 该分量是死项，删或重标定）
3. **单测**：量级预算表写成代码常量，改动即触发 review

> **这是我上一轮修 K4 时引入的回归** —— 把 §12 的三个名词替换成上面那张三行塑形表时，
> **丢掉了原 `intent-rl-reward.ts` 的事件与终局项**。评审指出后核对属实。

**核对 `src/nn/intent-rl-reward.ts:33-43`**（原文照抄）：

```ts
KILL: 4.0,   LIFE_LOSS: -5.0,       BASE_WALL_LOSS: -3.0,
CLEAR_STAGE: 50.0,  BASE_DESTROYED: -50.0,  LIVES_EXHAUSTED: -30.0,

```

**后果（Reward Gaming，可构造的反例）**：
冲进敌群送死、但死时恰好在目标格邻域 ⇒ 拿 `+1.0`（到达），
**阵亡与基地失守的惩罚为 0**；且 `CLEAR_STAGE` 完全不在目标里
⇒ **RL 的目标函数与"通关"这件事无关**。PPO 必然训塌。

**定案 —— 总奖励 = 事件/终局项 + 目标空间塑形项**：

```python
R_total = R_event（事件/终局，稀疏）  +  R_shaping（§12.3 三分量，稠密）
```

**R_event 直接继承现有、已在 75% 基线上验证过的量级（不重新调参）**：

| 事件 | 值 | 备注 |
|---|---|---|
| `CLEAR_STAGE` | **+50.0** | 终局正反馈 |
| `BASE_DESTROYED` | **−50.0** | 终局重罚 |
| `LIVES_EXHAUSTED` | **−30.0** | 终局重罚 |
| `LIFE_LOSS` | **−5.0** | 单次阵亡 |
| `BASE_WALL_LOSS` | **−3.0** | 基地环墙被拆 |
| `KILL` | **+4.0** | 击杀 |
| `TIMEOUT` | **−1.0** | 轻罚防挂机（**评审漏了这条**） |
| `BRICK_CLEAR` / `PICKUP` | 0.5 / 2.0 | 保留 |

**量级关系的判据（不是拍脑袋的比值）**：

| 关系 | 定案 |
|---|---|
| 事件 vs 塑形 | **二者同量级，互不压倒**。单局塑形累计 ≈ 合约数 × 1.8；<br>dt=180 ⇒ 约 29 个合约 ⇒ 累计 ≈52 ⇒ 与 `CLEAR_STAGE` 50 同量级。<br>⇒ 可接受，但**必须在 T9a 实测** |
| **γ_step 的折扣交互** | `γ_step = 0.995^dt` ∈ [0.30, 0.55]（§12.1）。<br>**裸折扣下终局信号在局初被折到 ≈0**，靠 **V(s) bootstrapping** 回传。<br>⇒ 终局项**必须**配 value 头才能学到 —— 这是 `value` 头不可省的第二个理由 |
| 比例是否要扫 | 若 T9a 出现"到达率高但胜率低" ⇒ 塑形偏强 ⇒ 扫 `R_shaping × {0.3, 0.5, 1.0}` |

**⚠️ 不接受评审提出的"归一化到 +5 / −5 / −1 / +0.5"**：
那会把事件项压到塑形的 **1/4**，从"无终局信号"翻到另一个极端"塑形压倒终局"。
现量级已在 intent RL 上产出 75%，**不要为了表格好看重调已验证的常数**。

**验收（挂 T9a，防 Reward Gaming）**：

1. **反例单测**：构造"冲进敌群送死 + 死时在目标格邻域" ⇒
   断言该窗口 `R_total < 0`（阵亡 −5 必须压过到达 +1）
2. **死亡率不升**：T9a 的 60-seed 上，goal 策略的**平均阵亡次数不得高于** God-AI 基线
3. **方向一致**：`R_shaping` 累计与 `episode_return` 的秩相关须 **> 0**
   （塑形不能与真目标反向）

#### T12.2 解法（两条，建议**同时**实现）

**方案 A — 决策记录（推荐，最稳健）**
把 goal 决策本身当作**输入**记入 replay 流（与 `AGENTS.md` §2.3 "input recordable"
一致，字段与 §6.1 的契约对齐）：决策时刻记录 `(tick, cell, T, engage, premiseLabel)`。
（**已按 §6.1 删除 `targetCell` / `K`** —— 二者随 target/K 头一起被砍，记录它们只会产生僵尸字段。）
回放时**直接重放决策序列**，**不重跑网络** ⇒ 与墙钟无关，天然 byte-identical。
（措辞修正，评审 k10：旧版写"重跑网络"语义不通——决策已记录就不需要重跑，
而这**正是方案 A 的意义**。）
- 附带好处：回放体积比逐帧 obs 小得多（每 150–300 tick 才一条）

**方案 B — 确定性边界应用（作为 A 的补充保险）**
1. obs 在**确定性 replan tick 当场快照**传入 worker（**不是** worker 启动时的"当前"世界
   —— 评审 F14，否则与训练分布漂移）
2. worker 结果暂存，**下一边界 tick 才生效**
3. **超时回退**：超过 `T_deadline` 未返回 ⇒ 沿用上一 goal；仍无 ⇒ God-AI 兜底（§9.2.1）
4. 回退路径同样**确定性**（由 tick 与超时常数决定，不由墙钟抖动决定）

#### T12.2.1 ⚠️ A 与 B 解决的是**两件事**，缺一不可（评审 A6）

评审指出：**方案 A 保住了 Replay，但没保住 Live 的跨终端一致性** —— 这条成立。

| 场景 | 桌面（前向 100 ms） | 手机（前向 250 ms） | 后果 |
|---|---|---|---|
| **Live 实机** | tick 156 收到结果并切换目标 | tick 165 才切换 | 同 seed 下，156–165 tick 期间<br>两者动作不同 ⇒ **局内物理分叉**<br>（是否命中、是否吃到道具） |
| **Replay 回放** | ✅ 方案 A 已覆盖（记录决策序列） | 同 | byte-identical |

⇒ **方案 A 只解决"录下来的能重放"，不解决"同一 seed 在不同设备上实机结果不同"。**

**定案 —— A 与 B 不是二选一，而是互补，两条都要**：

| 层 | 由谁保 | 机制 |
|---|---|---|
| **Replay 可复现** | **方案 A** | 决策记入 replay 流，回放不重跑网络 |
| **Live 跨终端同构** | **方案 B 的 "固定提前量对齐"** | 见下 |

**固定提前量调度（Fixed Lead-Time，沿用方案 B 第 2 条并钉死参数）**：

```
T_dispatch  = 决策派发 tick（确定性，由心跳/事件触发决定）
T_apply     = T_dispatch + T_lead          ← 严格固定，与硬件无关
T_lead      = 20 tick ≈ 333 ms（留足移动端余量；与 §16.5 实测对齐后可调）

· 提前返回（桌面 6 tick 就完成）⇒ 主线程暂存，到 T_apply 才生效
· 超时未返（超过 T_lead）      ⇒ 在 T_apply 触发确定性回退（方案 B 第 3 条）
```

⇒ 决策的**生效时刻由 tick 决定，不由墙钟决定** ⇒ 不同算力设备上物理演化同构。

**验收新增第 5 条（挂 CI）**：
> **跨算力对齐测试**：注入两组不同的固定前向延迟（如 6 tick 与 15 tick），
> 断言两者在 `T_apply` 之后的**世界状态逐 tick 一致**（不只是 replay 一致）。

> **诚实边界**：这只保证"已返回的结果在同一 tick 生效"。
> 若某设备**持续超时**（每次都走回退），它仍会与不超时的设备分叉 ——
> 这是算力不足的固有结果，不是 bug。缓解靠 §16.4 的瘦身档 / 分帧摊还。

# Part VI — 部署性能

## 16. 推理性能预算（2026-08-29 实测）

### 16.1 ⚠️ 先更正：文档里的 41.1 ms 是过期数字

`docs/nn.progress.intent.md` §19 记录的 **41.1 ms / 0.91 G MAC/s** 在当前环境下**不可复现**。
本工作区两次实测：

| 测量 | 单次前向 | implied MAC/s | 命令 |
|---|---|---|---|
| 全量基准（200 预热 + 4000 迭代） | **109.7 ms** | 0.34 G | `bun tools/bench-intent-infer.ts`（7m37s） |
| 低迭代复测（100 预热 + 6×100，取中位数） | **170.0 ms** | 0.22 G | 探针，6 样本 163–173 ms |

⇒ **当前真值 ≈ 110–170 ms（0.22–0.34 G MAC/s）**，比文档值慢 **2.7–4.1 倍**。
**凡引用 41.1 ms 的推算（含旧计划的"÷24 → 1.71 ms/tick"）全部作废。**

### 16.2 目标网络的算力变化：**+0.108%，可忽略**

| 项 | MACs | 占主干 |
|---|---|---|
| 主干（stem + 8×ConvMixer） | 37.5 M | 100% |
| **新增 goal 热图**（1×1 conv, 64→1 @ 676） | 43,264 | **0.115%** |
| 删除 `enemy_head`(137×5) + `anchor_head`(137×16) | −2,877 | −0.008% |
| **净变化** | **+40.4 K** | **+0.108%** |

> **更新（评审 P3）**：target 热图头已砍（§8.3.0b），故净变化从 +83.6 K 降到 **+40.4 K**
> （占主干 **0.108%**）。T / K 本就是标量头（各 137 参数），砍掉对算力无实质影响。

**答 Q1：目标网络与意图网络的前向成本实质相同。** 主干占 99.8%，头怎么改都无所谓。
真正决定实机性能的是**调度频率**与**是否在渲染线程**，不是头的形状。

### 16.3 答 Q2：2020 旗舰机能否 60 FPS？

**帧预算 = 16.67 ms。**

| 平台 | 单次前向（估/实测） | 折合丢帧 |
|---|---|---|
| 本工作区（桌面，实测） | 110–170 ms | 7–10 帧 |
| 2020 旗舰（SD865 / A13 / K990，标量 f32 JS，单核） | **150–375 ms**（按 0.10–0.25 G MAC/s） | **9–22 帧** |

> 手机数字是**外推**，未经实机验证 —— 必须用 §16.5 的协议上机实测。

**结论：同步放渲染线程 ⇒ 不可能 60 FPS，任何 replan 周期都不行。**
即使 replan=30（每 0.5 s 一次），也会每半秒丢 9–22 帧。

### 16.4 让它可行的四个条件（按优先级）

1. **Worker 卸载（首选）**
   前向放 worker，主线程从不阻塞。延迟对外不可见。
2. **★ 承诺制让延迟变得可容忍 —— 这是本设计的关键协同**
   网络回答的是"**接下来 200–300 tick 我该站在哪**"，不是"这一 tick 我做什么"。
   250 ms（≈15 tick）的延迟对一个 200-tick 视野的问题**无所谓**；
   而逐 tick 反应式策略必须 16 ms 内拿到答案，根本无法卸载。
   ⇒ **契约/承诺不只是算法设计，它同时是部署可行性的前提。**
3. **事件驱动调度（§6.3）**
   心跳 150–300 tick + 纯谓词门禁 ⇒ 前向从"每 0.5 s 一次"降到**约 0.2–0.6 次/秒**
   ⇒ 250 ms × 0.6 ≈ **单核 15%**，余量充足。
4. **分帧摊还（Worker 的替代方案）**
   ConvMixer 可在块边界切成 9 段（stem + 8 block），摊到 ~60 帧
   ⇒ **≈4.2 ms/帧**，落在 16.67 ms 预算内且留有余量。
   同样**只有在心跳给足 150–300 帧松弛时才成立**。

**瘦身档（可选）**：h=48 / d=6 ⇒ 主干 ≈18.9 M MACs（**0.50×**）
⇒ 手机约 75–190 ms。量级改善，但仍需配合 1/3/4 之一。

### 16.5 上机实测协议（T11，部署前必做）

1. 在目标机浏览器跑 `tools/bench-intent-infer.ts` 的同款负载（**降到 200 迭代**，避免手机超时）
2. 记录：**单次前向 ms**、连续 100 次的 p50 / p95（看降频）、机身温度
3. 用实测 MAC/s 回填 §16.3 表格，重算三种部署方案（Worker / 分帧 / 瘦身）的可行性
4. **判据**：Worker 方案下单核占用 <20%；分帧方案下每帧增量 <5 ms
